# 旧编辑器晚到的 onReady 把旧正文写进新打开的笔记

Status: needs-triage
Type: Bug
来源：V105-02 实现途中发现（2026-11-08），见 [`../../v1.0.5/spec.md`](../../v1.0.5/spec.md)「本版不做」。曾编号 V105-06；1.0.5 发布时还没决定是否纳入，所以挪到这里，没有进 1.0.5。进入某个版本时再按那个版本重新编号。**这是个可能写坏文件的数据安全问题，建议下一版优先处理。**

## 现象

一篇笔记的所见即所得编辑器刚挂上、Milkdown 还没触发 `onReady` 时，用户打开了另一篇。这时旧编辑器晚到的 `onReady` 会把**旧笔记的正文**写进新笔记的状态：新标签页显示的是旧笔记的内容。

后果可能是**数据丢失**：用户在这个标签页里一输入，自动保存就会把旧正文写进新笔记的文件。而且请求带的 `baseHash` 是新文件的，冲突检测拦不住，后端会接受这次保存。

## 根因（V105-02 的分析，代码已核对）

`frontend/src/App.tsx` 里 `MarkdownEditor` 的 `onReady` 回调：

```tsx
onReady={(markdown) => {
  setContent(markdown);
  if (content === loadedContent) {
    setLoadedContent(markdown);
  }
}}
```

- 回调没有核对上报的是哪篇笔记。`MarkdownEditor` 把 `onReady` 存在 `onReadyRef` 里，每次渲染都换成最新的那个（`MarkdownEditor.tsx:70`）。所以旧编辑器实例（比如 `AnimatePresence` 离场动画期间还挂着的那个）晚到的上报，调用的是**当前**这次渲染的回调。
- 新笔记刚加载时 `content === loadedContent`，所以 `setLoadedContent(旧正文)` 也会执行。界面认为「没有未保存的修改」，用户看不出任何异常，直到一输入，旧正文就被存了进去。

## 复现

- **jsdom 里复现过**（V105-02 会话，用改动前的代码）：恢复标签页 `a.md`；在 `ready` 之前排队一个 `onOpenFilePath` 请求（`日记/双击.md`）；就绪后，`日记/双击.md` 的标签页显示的是 `a.md` 的正文。
- **没有在真实的 1.0.4 上复现过。** 1.0.4 里「双击 .md 启动，同时有恢复的标签页」走的是同一段代码。
- V105-02 只在启动这条路上避开了它：排队的那篇打开之前不挂编辑器，编辑器只挂一次。其他「刚打开一篇又马上打开另一篇」的情况，比如在文件树里快速连点两篇，仍然可能触发。

## 建议修法（未决定）

让 `MarkdownEditor` 的 `onReady` 带上 `noteKey`。App 收到上报时，`noteKey` 不是当前 `editorNoteKey` 的就忽略。`onChange` 也可能有同样的问题，修的时候一起核对。

## 验收

- 按项目的缺陷流程来：先写测试，在改动前的代码上因为这个缺陷本身而失败；修好以后通过。
- 至少覆盖两种情况：启动时排队打开；就绪以后在文件树里快速连续打开两篇。
- 打包版上实际试一次快速连开两篇，确认文件内容没有被写错。
