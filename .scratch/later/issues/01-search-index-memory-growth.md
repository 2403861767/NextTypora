# 搜索索引的内存随笔记总量线性增长

Status: needs-triage
Type: Change
来源：1.0.5 grilling（2026-11-08）Q5，见 [`../../v1.0.5/spec.md`](../../v1.0.5/spec.md)「本版不做」

## 现象

`IndexService` 把每篇笔记的全文小写副本（`IndexedNote.body`）、标题、路径、frontmatter 和标签都放在内存里。所以后端内存随笔记总量线性增长。

实测（5000 篇，40MB，内容是中英混排）：

| 后端 | 小工作区 | 5000 篇 | 差值 |
| --- | --- | --- | --- |
| 1.0.4（`-jar`，默认 JVM 参数） | 158MB | 262MB | +104MB |
| 1.0.5 调优后（V105-04、V105-05 的参数 + 类缓存） | 99MB | 137MB | +38MB |

调优以后，每 1000 篇大约多 8MB。1.0.5 的内存目标只针对 1000 篇以内的工作区，所以这张票不在 1.0.5 范围内。

## 可能的方向（未决定）

- 正文逐篇压缩后存放，搜索时再解压。注意改存 UTF-8 的 `byte[]` 没用：Java 对纯拉丁文本本来就按单字节存，中文按 UTF-16 是每字 2 字节，换成 UTF-8 反而是 3 字节。压缩能省多少、解压全部正文会让搜索慢多少，都要实测。
- 正文不进内存，只留标题、路径和标签；搜正文时回读文件。内存大幅下降，但正文搜索会变慢很多，大工作区尤其明显。
- 设一个上限，超过就退回上一种方式。

每个方向都会影响搜索的行为或速度，triage 时要先拿到真实用户的工作区规模。grilling 时没拿到：开发机设置里的工作区是 `test/` 测试目录。

## 怎么测

`npm run perf:measure -- --big-vault`（V105-01）会生成一个 5000 篇的工作区，测启动时间和内存占用。搜索耗时可以参考 grilling 时用过的方法：等索引建完，每个查询词跑 15 轮取平均。
