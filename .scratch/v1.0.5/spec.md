# NextTypora 1.0.5 — 启动时间与内存占用

Status: resolved

## 本版主题

**让应用打开得更快、占的内存更少。** 只做性能，不加功能，也不顺手修无关的 bug。性能工作途中发现的问题照 1.0.4 的做法单独开工单，再决定进不进这一版。

## 口径

「启动时间」「内存占用」按 [`GLOSSARY.md`](../../GLOSSARY.md) 的定义：

- **启动时间**：从双击图标（或一篇笔记）到上次工作区的文件树和上次打开的笔记正文都显示出来。以热启动为准；冷启动只记录，不定目标。
- **内存占用**：任务管理器里本应用这一组进程（含 Java 后端）的专用工作集之和，打开工作区后空闲 20 秒时读取。
- 只测打包版（`release/win-unpacked`），开发版的数字不算。工作区用 `test/e2e-vault` 的副本（复制到仓库外，不要原地用）。

## 基线：1.0.4 实测（2026-11-08）

按完整口径测：文件树出现、**并且**恢复的那篇笔记正文也显示出来，才算启动完成。用 `npm run perf:measure`（V105-01）测，原始数据在 [`test/perf/results.json`](../../test/perf/results.json) 的 `1.0.4` 下。

机器：i5-12500H，12 线程，16GB 内存（系统报 15.7GB），Windows 11（10.0.26200）。打包版 1.0.4（`release/win-unpacked`，构建自 `c244a95`，测前 `verify:release` 通过）。每轮都用新的 user-data-dir 和新的 e2e-vault 副本，恢复一个标签页 `ascii-notes.md`；先空跑一轮暖缓存，再测三轮热启动取中位数。

| --- | --- |
| 后端从 JVM 启动到 Spring 就绪 | 3.5 秒（其中 Spring 2.7 秒，JVM 自身约 0.8 秒；取自后端日志） |
| 主窗口开始创建 | 4.1 秒，要等后端健康检查通过（[`main.js`](../../electron/main.js) 的 `whenReady` 里是串行的） |

## 目标

在上面的机器上用 e2e-vault 测：

- **启动时间 ≤ 2.0 秒**
- **内存占用 ≤ 250MB**

内存目标原先是 220MB。那是按只测到文件树的 279MB，减去后端调优能省的约 60MB 定的。V105-01 按完整口径重测，基线变成 305.6MB；多出的约 27MB 是渲染恢复的那篇笔记占的，本版计划里没有针对它的改动。同样省下约 60MB，按新基线对应的就是 250MB 左右。2026-11-08 用户确认改为 250MB。

5000 篇工作区的数字只记录，不定目标。本版的内存目标只针对 1000 篇以内的工作区。

## 实验：方案依据

只测后端（用打包里的 JRE 直接起后端，从启动到打出端口；内存为空闲 8 秒后的专用工作集）：

| 启动方式 | 打出端口 | 内存 | 5000 篇时内存 | 5000 篇搜索平均 |
| --- | --- | --- | --- | --- |
| 1.0.4 现状（`-jar` 胖 jar，默认参数） | 3.5 秒 | 158MB | 262MB | 17ms |
| + 精简参数（SerialGC、只用 C1、初始堆 16MB） | 2.6 秒 | —¹ | — | — |
| + 基础类缓存 + 精简参数 | 2.5 秒 | —¹ | — | — |
| + 普通 classpath + 应用类缓存（AppCDS）+ 精简参数 | **1.1 秒** | **99MB** | **137MB** | 17ms |
| 同上但用默认的两级编译（C2） | 1.6 秒 | — | 149MB | 14ms |

¹ 这两行 grilling 时只记了总工作集（含共享页，分别是 126MB、122MB），没有记专用工作集，和其他行不能直接比。V105-04 的会话用同样的方法补测了专用工作集，分别是 100.9MB 和 100.0MB（当时另外两个会话在编译，只作参考）。所以内存的收益几乎都来自精简参数，基础类缓存本身基本不影响内存；原来以为要等应用类缓存做完才能到 99MB，其实不用。打包版的整体数字见「进度」一节。

几条结论：

- 打包时 jlink 精简出来的 JRE **没有 JDK 自带的基础类缓存**（`bin/server/classes.jsa`），JDK 的类每次都从头加载。应用类缓存必须建立在基础类缓存之上，没有它，`-XX:ArchiveClassesAtExit` 直接报 unsupported。
- 应用类缓存**不能用于 `-jar` 胖 jar**：Spring Boot 的嵌套 jar 由自定义类加载器加载，类缓存覆盖不到。所以后端必须改成普通 classpath 布局（应用类单独一个 jar，依赖放在 `lib/`）。
- 用相对 classpath 生成的类缓存，连同 JRE 整体搬到带空格和中文的路径下照样命中。**唯一的条件是 jar 的修改时间不变**：用 `cp -r` 复制（修改时间变了）时 JVM 报 `app.jar timestamp has changed`，然后不用缓存、按普通方式启动，不会出错；用 `cp -rp`（保留修改时间）时命中。
- 堆上限设 128MB 还是 512MB，空闲内存没有区别；SerialGC 只按实际使用量申请内存。
- 只用 C1 和两级编译相比，启动快 0.45 秒、内存少 12MB，搜索只慢 3ms，所以选只用 C1。
- 安装包体积：两份类缓存压缩后约 +9MB（应用类缓存 38.6MB 压到 6.9MB，基础类缓存 12.5MB 压到 2.3MB）。`flexmark-all` 带进来、实际用不到的 jar 有约 20MB（其中 icu4j 14MB，另有 pdfbox、fontbox、openhtmltopdf 等），去掉以后净减少约 11MB。

Electron 这一侧：

- `--disable-gpu` 只省 12MB，网络服务放进主进程只省 5MB，都不值得做。
- 渲染进程只占 48MB，JS 堆实际用了 11MB。后端和窗口同时启动以后，前端加载的 0.6 秒被后端的启动时间盖住了。

## 考虑过但没选

| 方案 | 预计效果 | 没选的原因 |
| --- | --- | --- |
| 后端改成 GraalVM 原生镜像 | 后端 0.2 秒以内、约 50MB | 构建链要换成 GraalVM，要补反射配置，138 个后端测试要在原生模式下再验一遍，打包时间明显变长。调优路线已经能把后端做到 1.1 秒、99MB |
| 去掉 Java 后端，逻辑搬进 Electron 主进程 | 省掉整个 JVM（调优后约 100MB，现在 158MB），安装包少约 100MB | 等于重写约 3600 行 Java 和全部测试，推翻 CLAUDE.md 定下的架构 |
| `--disable-gpu` | −12MB | 收益太小，还有滚动和渲染变卡的风险 |
| 网络服务放进主进程 | −5MB | 收益太小 |
| 后端用两级编译（C2） | 搜索快 3ms | 启动慢 0.45 秒，内存多 12MB |

以后如果要再往下压，原生镜像的数字最有吸引力。到那时先用 `perf:measure` 量一下调优后剩下的差距，再决定。

## 待在实现中确认

- **安装包是否保留文件修改时间**（V105-05）。**已确认：不保留。** electron-builder 打 NSIS 的 7z 时写死了 `-mtm=off`，安装包里不存修改时间，装出来的 jar 全是安装时刻，应用类缓存不命中（离线查了安装包，又经用户同意用临时 appId 的测试安装包实际装了一次）。用户选的处理方式不是原定的「首次启动时生成缓存」，而是构建时记下每个 jar 的大小、修改时间和 SHA-256，`main.js` 每次启动后端前把对得上的 jar 改回原来的修改时间（`electron/backendArchive.js`）。安装后第一次启动就命中，代价是那一次多约 0.13 秒算哈希。细节见 V105-05 的完成情况。
- **主题闪烁**（V105-02）。现在渲染进程要等后端健康检查通过以后才读偏好设置、应用主题。窗口提前显示的话，用户会先看到默认主题，再切到自己的主题。偏好设置走的是 IPC，不经过后端，所以可以提前应用。**已处理：** V105-02 把应用偏好设置挪到了等后端之前，有前端测试固定（主题在后端就绪之前就已应用）。

## 决定来源

2026-11-08 grilling（`/grill-with-docs`），两轮共九个问题，全部按推荐方案定：

1. 口径：见上文，已写进 `GLOSSARY.md`。
2. 路线：保留 Spring Boot + JVM，只调优。
3. 范围：只做性能。
4. 防回退：`perf:measure` 只报告和警告，不拦发布；不放进 `dist:verify`（那一步在打包前跑，测不到打包版）。
5. 大工作区：本版内存目标只针对 1000 篇以内，索引的线性增长单开工单。
6. 目标：2.0 秒 / 220MB。V105-01 按完整口径重测基线后，内存目标改为 250MB（2026-11-08 用户确认，原因见「目标」一节）。
7. 启动画面：去掉。
8. 框架升级：不放进本版，各开一张工单。
9. 前端瘦身：先不做，内存没达标再开工单。

技术参数（只用 C1、SerialGC、初始堆 16MB、堆上限 512MB）根据上面的实验确定，没有另外问。

这一版没有新增 ADR：上面几项决定都不难反悔，不满足写 ADR 的条件。为防止以后有人把后端改回 `-jar` 胖 jar、白白丢掉启动时间，V105-05 会让 `test:packaged` 检查类缓存是否命中，这是真正起作用的防线。`CLAUDE.md` 被 `.gitignore` 忽略、从没进过仓库（V105-01 时发现），写进去的注意事项只存在本地那份文件里，不能当作防线。

- **正式安装包没有实际安装。** 机器上装着正式的 1.0.3，用同一个 appId 的安装包会把它卸掉。V105-05 改用临时 appId 的测试安装包，验证了安装后类缓存命中、卸载后注册表还原；正式安装包的文件关联和安装界面这一版没有改动，也没有实测。
- **ZIP 发行包**（`npm run dist`）：ZIP 只存精度 2 秒的 DOS 时间，按设计由 `backendArchive.js` 在启动时改回修改时间，没有实测。
- **冷启动**（开机后第一次打开）：按口径只记录不定目标，这一版没有测。
- **`release/NextTypora-1.0.4-win-x64.exe` 不是 1.0.4。** V105-05 跑 `dist:setup` 时，它被覆盖成了当时的构建，文件名和版本号还是 1.0.4，内容却是 1.0.5 的改动。`latest.yml` 现在指向 1.0.5。不要把这个文件当 1.0.4 发出去；真正的 1.0.4 安装包要从 `c244a95` 重新打。
